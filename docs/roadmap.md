# ロードマップ

PDFto の計画を一元管理する。ロードマップは複数の**マイルストーン**で構成し、
各マイルストーンは複数の **issue**（具体的な作業単位）を持つ。
進め方の方針は [../CLAUDE.md](../CLAUDE.md) を参照。

**状態の凡例:** `todo` / `in-progress` / `done`
各 issue は、振る舞いを変える場合 `docs/specs/` にスペックを持つ。

---

## ふりかえりログ

マイルストーン完了ごとに「うまくいったこと / 課題 / 次に変えること」を記録する。
ここで決めたプロセス改善は CLAUDE.md に反映する。

### M0（MVP）
- **うまくいったこと:** コア（解析/質問/変換）を Web 層から分離できた。docling を
  遅延 import にしたことで、モデル無しでもテストが回る構成にできた。
- **課題:** 保存がインメモリ索引で、再起動で消える。変換が同期実行で重い PDF に弱い。
- **次に変えること:** 信頼性・運用性（M1）を次の焦点にする。振る舞いを変える issue は
  着手前にスペックを書く運用を M1 から徹底する。

### M1（信頼性と運用性）
- **うまくいったこと:** スペック駆動（spec → 合意 → 実装 → 検証 → 記録）を 4 issue で
  一貫して回せた。非同期化・TTL・Docker・ログ/エラーで運用性が大きく前進。Docker は
  `--network none` でオフライン変換を実証し、受け入れ条件を実機検証できた。
- **課題:** ジョブ索引・ストレージ索引が依然インメモリで、プロセス再起動やマルチ
  インスタンスに弱い（永続化は未対応）。Docker イメージが約 4.3GB と大きい。
  サンドボックスのプロキシ CA でコンテナビルドがハマり、検証に回り道した。
- **次に変えること:** 永続化（DB/オブジェクトストレージ）とイメージ軽量化は将来の
  issue として明示的に積む。M2（公開・連携）に進む前に、認証/レート制限の前提と
  なる「インスタンスをまたぐ状態共有」をどう扱うかを M2 スペックで先に決める。

### M1.5（状態の永続化）
- **うまくいったこと:** `Database` を薄い抽象として切り出し、`Storage` と
  `JobManager` を SQLite 化しても公開 API はほぼ不変に保てた。再起動を跨ぐ
  ドキュメント参照を実機で確認し、中断ジョブ復旧もユニットテストで担保。
  既存テストは `JobManager(db=...)` への小改修で済んだ。
- **課題:** 単一コネクション + Lock のため高負荷では直列化がボトルネックになり得る。
  ジョブ実行は依然プロセス内（マルチインスタンスでの分散実行は未対応）。
- **次に変えること:** M2 では「ジョブを投入したインスタンスが実行する」前提を
  明記して認証・レート制限を設計する。分散実行（共有キュー）が必要になった時点で
  別マイルストーン化し、`Database` 抽象を Postgres 等へ差し替える。

### M2（公開・連携の強化）
- **うまくいったこと:** 認証/レート制限・Webhook・バッチ・クライアントを各々
  スペック駆動で完走。ミドルウェアや薄いモジュール追加で実現し、`callback_url` や
  認証は「未設定なら従来挙動」のオプトインにできたため後方互換を保てた。クライアントは
  実サーバをスレッド起動して E2E テストでき、品質を担保できた。
- **課題:** レート制限・Webhook 配送がプロセス内（分散・再試行・配送永続化は未対応）。
  Web UI は認証有効時にキー入力欄が無く未対応。SSRF はスキーム/ホスト制限止まり。
- **次に変えること:** 公開機能の「分散対応（共有レート制限・ジョブキュー）」と
  「Webhook の再試行/永続化」をまとめて将来マイルストーン化する。次の焦点は変換品質
  （M3）。運用機能が出揃ったので、ここで実 PDF を使った品質検証の土台づくりに移る。

### M3（変換品質）
- **うまくいったこと:** OCR 言語選択・表精度・参照画像・OCR/LLM をスペック駆動で完走。
  実機検証で「OCR は機能しているが全面罫線表はページが画像分類される」「合成 PDF は表
  検出が不安定」といった事実を掴み、**コードよりスペックを先に現実へ合わせる**運用が
  機能した。EasyOCR の焼き込みでオフライン言語 OCR を実証。LLM 整形は anthropic 遅延
  import＋オプトインで、キー無しでも既定挙動・テストを壊さず追加できた。
- **課題:** docling の重い実変換は CI に載せられず、品質検証は opt-in/手動に留まる。
  LLM 整形は実 API 呼び出しを CI で検証できず（モック止まり）、大きな文書のチャンク
  分割も未対応。表構造の厳密な品質指標は未整備。
- **次に変えること:** 重い実変換・LLM の検証は「opt-in の実機スイート」を別途定義し、
  定期手動 or 専用環境で回す。次は運用の分散対応（共有状態・ジョブキュー・Webhook
  再試行）を新マイルストーン化するか、ここまでの全体ふりかえりに移る。

---

### M4（信頼性 UX・軽量）
- **うまくいったこと:** Redis/Celery を入れずに SQLite だけで「取りこぼさない（Webhook
  再試行/永続化）・追える（一覧 API）・やり直せる（再実行）」を実現。既存の `Database`
  抽象とミドルウェア/スレッドの型（cleanup と同形）を再利用でき、依存も外形も増やさず
  に済んだ。ジョブにオプションを永続化したことで再実行が成立し、再起動耐性も得た。
- **課題:** 一覧は offset ページングで深いページに弱い。再試行・配送は依然プロセス内
  （マルチインスタンス分散は引き続き非対応）。テスト追加でレートリミッタの共有状態が
  429 を誘発し、フィクスチャでの毎テストリセットが必要だった（テスト分離の教訓）。
- **次に変えること:** UX の核は API として出揃ったので、次は M5（UI の追随）でこれらを
  ブラウザから使えるようにする。分散対応は需要が出た時点で別マイルストーン化する。

### M5（UI の追随）
- **うまくいったこと:** M4 で出した一覧/再実行/バッチ API を、バックエンド無改修で
  ブラウザから使えるようにできた（履歴・再実行・API キー・バッチ）。`authHeaders` と
  `downloadFile`（認証付き Blob 保存）を共通化し、各機能で再利用できた。認証キーは
  「未入力なら従来どおり」のオプトインで既定挙動を壊さない。
- **課題:** UI は自動テスト対象外でスモーク確認に依存（ブラウザ E2E は未整備）。キーは
  `localStorage` 平文。バッチ UI は共通オプションのみ（高度設定は API/対話に委譲）。
- **次に変えること:** UI の回帰は重要機能だけでも軽量なブラウザテスト（Playwright 等）を
  将来検討。次は M6（配布・軽量化）で導入の手軽さを上げる。

### M6（配布・軽量化）
- **うまくいったこと:** クライアントを `pyproject.toml` 付きの配布物（`pdfto-client`・
  依存ゼロ・単一モジュール）にし、`pip install ./client/python` と `python -m build`
  をクリーン環境で検証。Docker はマルチステージ化し、torch を CPU 専用 index から
  導入して CUDA/nvidia スタック（約 3–4GB）をイメージから排除。`--network none` で
  docling 既定変換と焼き込み EasyOCR の両方がオフライン動作することを実機確認できた。
- **課題:** イメージは依然大きい（焼き込み ML モデル約 1.5GB＋torch/OpenCV スタックが
  支配的で、これは仕様上不可避）。サンドボックスの空きディスクが少なく旧構成（CUDA
  単一ステージ）の実ビルドができず、旧/新の数値比較は未取得（CUDA 不在を軽量化の根拠と
  した）。実ビルド検証は egress プロキシの CA 注入が必要で重い。
- **次に変えること:** さらなる軽量化が要るなら「モデルを焼き込まない slim タグ＋初回 DL」
  や docling の最小エクストラ選択を検討。実ビルド検証は CI（ネットワーク制約のない環境）に
  寄せると再現性が上がる。次は M7（検証スイートの拡充＝②）へ。

### M7（検証スイートの拡充）
- **うまくいったこと:** opt-in 実機テストを実変換の全出力形式＋ページ範囲に拡張し、実 LLM は
  専用フラグ＋キー必須で別ファイルに分離（誤起動・課金を防止）。表抽出は「本文付き・罫線控えめ」
  サンプルなら docling が確実に表として抽出することを spike で確認し、Markdown 表を解析した
  **セル復元率**という品質指標で回帰を捉えられるようにした。実行して初めて分かる挙動
  （text 形式が画像のみページで空＝spec 0012）もテストが検出し、前提を正せた。
- **課題:** 実機テストはモデル DL を含み 1 回 3〜4 分（初回）と重く、本サンドボックスでは
  ネットワーク/ディスク制約がある。実 LLM はキーが無く本環境では skip 確認に留まる。回帰
  サンプルは単純表 1 種のみ（結合セル・複数ページ・複雑表は未カバー）。
- **次に変えること:** 重い実機テストは将来 CI（専用環境）で定期実行すると回帰検出が安定する。
  サンプルは必要に応じて複雑表へ拡張。LLM 実テストは鍵のある環境で手動実行。

### M8（入力フォーマット拡張）
- **うまくいったこと:** docling が多形式対応なことを spike で確認（HTML/PNG/DOCX）し、コア
  （converter/storage）と Web 層（受け口/解析/質問）を 2 issue に分けて段階導入。「コアは
  Web 非依存」の境界を保ったまま、まずコアを一般化（M8-1）→ Web を配線（M8-2）できた。
  解析フラグ＋形式 kind で質問を自然に出し分け（Office は OCR/表/ページを出さない、画像は
  OCR を出す）。`source_extension` はデフォルト空で後方互換、DB 列名は据え置きでマイグレ不要。
- **課題:** 実際に有効な形式は docling のバックエンド導入状況に依存（環境差）。opt-in 実変換は
  HTML のみ追加（Office/画像の実変換は spike では確認済みだが回帰テスト未追加）。`do_ocr` が
  従来から無条件追加だった件は、テストを書いて初めて気づけた（出し分けの前提を是正）。
- **次に変えること:** Office/画像の opt-in 実変換テストも将来追加。形式別の高度オプション
  （PPTX ノート等）は需要次第。次は M9（CLI ツール）。

### M9（CLI ツール）
- **うまくいったこと:** M6 の依存ゼロパッケージを土台に、`pdfto_client` へ `main()` を足し
  `[project.scripts] pdfto` を登録するだけで CLI を提供（標準ライブラリのみ）。`health`/
  `convert`（stdout・`-o`・`--ocr`・`--no-table`）を実装し、既存のサーバスレッド fixture を
  再利用してテスト。一時 venv で `pip install` → `pdfto --version` まで実機確認。
- **課題:** CLI は API サーバ必須（依存ゼロを守るため docling 同梱の直接変換は非採用）。
  バッチ/対話フローは未対応。stdout のバイナリ出力は `capsysbinary` でテスト。
- **次に変えること:** 需要があればバッチや「直接変換（重いがサーバ不要）」モードを別途検討。

### 残っている構造的な課題
- **状態がプロセス内に閉じている**：SQLite 永続化で再起動耐性は得たが、レート制限・
  Webhook 配送・ジョブ実行はインメモリ/プロセス内で、マルチインスタンス分散は未対応。
- **検証の自動化に限界**：docling/LLM の実変換は CI に載せられず、品質は opt-in/手動。
  表構造の定量指標や大きな文書のチャンク分割も未整備。
- **Web UI の機能カバレッジ**：認証有効時の API キー入力欄が無いなど、UI は API に
  追随しきれていない部分がある。
- **イメージサイズ**：モデル焼き込みで Docker イメージが大きい（軽量化は将来課題）。
